# 使用 Codex + PHP + MySQL 搭建多语言外贸网站：从零开发到虚拟主机部署完整指南

对于外贸企业来说，一个优秀的独立网站不仅需要展示产品，还需要具备多语言支持、搜索引擎优化、客户询盘
![Codex驱动的多语言外贸建站指南](https://cdn.jsdelivr.net/gh/smalljialive/Blogimg@main/img/e4b9a9acc741b76ed229c4dc641e43b2.png)
管理以及 Google Ads 广告转化追踪等功能。

最近，我一直在使用 OpenAI Codex 开发自己的 B2B 外贸独立网站。在整个开发过程中，我逐渐调整了技术架构，从最初计划使用的 Next.js + Node.js，改成了更适合虚拟主机的原生 PHP + MySQL 方案。

这篇文章将分享我的建站思路、技术选型、开发流程以及部署方案，希望能够帮助同样想使用 AI 编程工具搭建外贸网站的朋友。

## 一、为什么最终选择 PHP，而不是 Next.js？

最初，我计划采用以下技术栈：

* Next.js + React：实现网站前端页面
* Node.js：处理后台服务和 API
* MySQL：存储产品、文章和客户询盘
* Prisma：进行数据库管理
* Nginx + PM2：管理网站服务
* 阿里云 ECS：部署网站
* GitHub + Codex：进行 AI 辅助开发和版本管理

这套方案适合有服务器管理权限的项目，但随着实际部署需求明确，我发现它并不适合我目前使用的虚拟主机。

我的主机使用普通虚拟主机管理面板，主要提供 PHP、MySQL、FTP 和 phpMyAdmin，并没有像云服务器那样自由安装后台运行环境的权限。

因此，我决定重新调整技术方案。

### 最终采用的技术架构


| 技术         | 用途                         |
| ------------ | ---------------------------- |
| PHP          | 网站后端逻辑及服务端页面渲染 |
| MySQL        | 产品、文章、询盘和管理员数据 |
| PDO          | 安全连接与操作 MySQL         |
| HTML5 + CSS3 | 网站页面结构与样式           |
| JavaScript   | 前端交互                     |
| GitHub       | 源代码版本管理               |
| OpenAI Codex | AI 辅助开发、测试和修复      |
| FTP / FTPS   | 上传网站文件                 |
| phpMyAdmin   | 导入、管理和备份数据库       |

使用这套架构最大的好处，就是部署相对简单。

**网站在本地完成开发后，只需要将 PHP 网站文件上传到虚拟主机，再使用 phpMyAdmin 导入 SQL 数据库，就可以在已有 PHP/MySQL 环境中运行。**

不需要在生产主机上安装 Node.js、Composer、PM2，也不需要通过 SSH 执行复杂的构建和部署命令。

当然，前提是网站所需的 PHP 版本、扩展和 URL 重写能力与虚拟主机兼容。

## 二、网站需要实现哪些功能？

我的网站主要面向海外工程机械客户，属于典型的 B2B 产品展示与询盘型网站。

网站不仅要看起来专业，还需要让海外客户方便地找到产品，并通过 WhatsApp、电子邮件或询盘表单联系销售人员。

### 1. 前台功能

主要包括：

* 首页：展示企业优势、核心产品、工程案例和联系方式
* 产品分类：按照设备类型展示不同产品
* 产品详情：包含设备型号、技术参数、图片、应用场景和 PDF 资料
* 工程案例：展示产品的实际应用和项目案例
* 文章中心：发布产品知识、行业资讯和采购指南
* 服务页面：介绍安装、培训和售后支持
* 关于我们：展示企业介绍与业务能力
* 联系我们：提供表单、WhatsApp、邮箱等联系方式
* 多语言切换：让不同国家的客户使用对应语言访问网站

对于工程机械行业，产品详情页面尤其重要。

例如，一台混凝土搅拌泵的详情页，不能只有图片和几句简单介绍，还应该包括实际型号、产能、技术参数、适用场景、常见问题和明确的询盘按钮。

### 2. Admin 后台管理系统

为了避免每次更新内容都需要修改 PHP 文件，我决定开发独立的 Admin 管理后台。

后台规划支持：

* 产品与产品分类管理
* 产品型号和参数表管理
* 图片与媒体资源管理
* 多语言内容管理
* 文章及工程案例管理
* FAQ 常见问题管理
* SEO 标题和描述管理
* 客户询盘管理
* 网站首页、导航和页脚设置
* 管理员登录和权限管理
* Google Analytics、Google Ads 等追踪代码配置

最终目标是让网站管理员不懂编程也可以更新产品信息、上传图片和发布文章。

## 三、使用 Codex 开发网站的正确流程

在实际开发过程中，我发现 AI 编程最重要的不是一次生成多少代码，而是能不能保持架构清晰、测试充分，并且允许随时回滚。

如果直接对 Codex 说：

“帮我做一个完整的多语言外贸网站。”

AI 可能会生成大量代码，但后续很容易出现数据库字段不统一、前后台接口不匹配、页面结构混乱等问题。

因此，我采用分阶段开发的方式。

### 我的 13 个开发阶段


| 阶段 | 开发内容                      |
| ---- | ----------------------------- |
| 1    | 整理项目需求和技术文档        |
| 2    | 创建 GitHub 仓库              |
| 3    | 配置本地 PHP 开发环境         |
| 4    | 创建本地 MySQL 数据库         |
| 5    | 规划 PHP 网站架构             |
| 6    | 设计并建立数据库结构          |
| 7    | 开发 PHP 后台业务接口         |
| 8    | 开发 Admin 管理后台           |
| 9    | 开发多语言前台页面            |
| 9.5  | 优化网站 UI、移动端和产品图片 |
| 10   | 功能测试、安全检查及 SEO 检查 |
| 11   | 制作 FTP 部署文件包           |
| 12   | 上传虚拟主机并导入数据库      |
| 13   | 上线后维护和持续优化          |

每个阶段都有明确的开发目标和验收要求。

我采用的工作方式是：

**编写文档 → Codex 分析 → 分批开发 → 统一测试 → Git 提交 → 进入下一阶段。**

通过这种方式，即使某个阶段出现问题，也能定位到具体模块，而不需要重新修改整个网站。

## 四、PHP 网站应该如何设计架构？

虽然不使用 Laravel 等完整框架，但我仍然希望网站代码具备清晰的模块结构。

因此，我采用 PHP 分层架构。

主要包括：

**Router（路由层）**

负责根据访问 URL，将请求分发到对应控制器。

**Controller（控制器层）**

负责接收用户请求、调用业务逻辑，并返回 HTML 或 JSON。

**Service（业务服务层）**

处理产品发布、询盘提交、参数验证等业务规则。

**Repository（数据访问层）**

通过 PDO 操作 MySQL 数据库。

**View（模板层）**

负责输出网站页面，实现 PHP 服务端渲染。

整个工作流程可以理解为：

`<span>用户请求 → PHP 路由 → 控制器 → 业务服务 → MySQL → HTML 页面</span>`

这种方式既保留了程序的可维护性，又能避免在服务器上依赖额外的 Node.js 运行环境。

另外，网站必须做好基础安全措施，包括 PDO 预处理查询、Session 登录、CSRF 防护、后台权限控制、文件上传校验以及敏感配置文件保护。

## 五、多语言网站应该怎么实现？

对于面向海外客户的外贸网站，多语言功能不能只停留在页面上的一个翻译按钮。

我更倾向于使用独立语言 URL 的方案。

例如：

* `<span>/en/</span>`：英文首页
* `<span>/es/</span>`：西班牙语首页
* `<span>/en/products/</span>`：英文产品列表
* `<span>/es/products/</span>`：西班牙语产品列表
* `<span>/en/products/concrete-mixer-pump/</span>`：英文产品详情

每种语言都拥有自己的页面 URL、标题、描述和正文内容。

数据库也需要支持不同语言的内容存储，而不是直接把不同语言的文字混合保存。

### 多语言 SEO 的关键设置

每个语言页面都需要考虑：

1. 独立的 SEO Title 和 Meta Description
2. 正确的 Canonical 标签
3. Hreflang 多语言对应关系
4. 对应语言的图片 Alt 文本
5. 独立且规范的 URL
6. 多语言 Sitemap
7. 正确的内部链接与语言切换逻辑

需要特别注意：如果某个产品还没有完成西班牙语翻译，就不应该直接生成一个内容错误或大量重复的西班牙语页面供搜索引擎收录。

## 六、为什么要提前规划 SEO 和 GEO？

以前做网站，可能会把 SEO 放到网站上线之后再优化。

但是使用 Codex 开发网站时，我认为更好的方式是：

**在数据库设计和页面架构阶段，就把 SEO 与 GEO 所需的功能考虑进去。**

SEO 主要帮助网站获得传统搜索引擎的自然流量。

GEO 则更关注让网站信息清晰、可信、结构化，从而更容易被生成式搜索系统理解和引用。

### 我重点规划的 SEO 功能

* 自定义页面 SEO 标题
* Meta Description
* 规范化 URL
* XML Sitemap
* Robots.txt
* 301 重定向
* Breadcrumb 面包屑导航
* Open Graph 分享信息
* 产品和文章 Schema 结构化数据
* 图片 Alt 与 WebP 优化
* 产品之间的内部链接
* 多语言 Hreflang

### GEO 内容优化方向

对于工业设备网站，我更关注真实、有用的技术内容。

例如，围绕混凝土搅拌泵，可以制作：

* Concrete Mixer Pump Buying Guide
* Diesel vs Electric Concrete Mixer Pump
* How to Choose Concrete Pump Capacity
* Concrete Mixer Pump Technical Specifications
* Common Concrete Pump Problems and Solutions

这些文章应包含真实的技术参数、适用环境、使用建议和常见问题，而不是单纯重复产品关键词。

需要说明的是，Schema 和内容结构优化能够改善机器对网页的理解，但并不能保证网站一定被 AI 搜索引用。

## 七、Google Ads 转化追踪必须提前设计

我的网站主要用于外贸产品推广，因此 Google Ads 转化追踪也是一个重要功能。

客户进入网站后，不一定会提交传统表单。

不少海外客户更喜欢直接点击 WhatsApp 联系销售人员，也有客户通过电子邮件咨询。

因此，我希望网站能区分不同的客户行为。


| 客户行为      | 追踪方式                   |
| ------------- | -------------------------- |
| 点击 WhatsApp | 记录 WhatsApp 点击事件     |
| 点击电子邮件  | 记录邮箱点击事件           |
| 提交询盘表单  | 后端确认成功后记录转化     |
| 进入感谢页    | 验证实际表单提交来源       |
| 产生有效询盘  | 后台或人工核实客户质量     |
| 形成合格商机  | 通过允许的方式回传转化数据 |

另外，可以在符合隐私和同意要求的前提下，记录 GCLID、GBRAID、WBRAID、UTM 参数以及首次访问页面等信息。

这样，在分析广告效果时，就不仅能看到客户点击了多少次按钮，还能进一步评估哪些广告实际带来了有效询盘。

需要注意，**WhatsApp 点击不等于有效询盘，表单点击也不等于成功提交。**

如果把所有点击行为都当成高质量转化，可能会影响 Google Ads 的自动出价优化。

## 八、如何把 PHP 网站部署到虚拟主机？

这是我从原先 Node.js 方案改为 PHP 方案的重要原因之一。

我的目标是尽可能简化部署过程，让整个网站能够通过普通虚拟主机管理面板完成上线。

### 第一步：检查虚拟主机环境

首先需要确认：

* PHP 版本与扩展
* MySQL 数据库版本
* FTP 或 FTPS 连接方式
* phpMyAdmin 是否可用
* 网站根目录位置
* HTTPS/SSL 配置
* URL 重写规则支持情况
* 文件上传大小和目录权限

如果主机环境无法满足网站的基本运行要求，应该在本地开发阶段解决兼容性，而不是上线之后才发现问题。

### 第二步：在本地完成开发与测试

所有核心功能先在本地测试。

包括：

* PHP 语法检查
* 产品增删改查
* 后台登录
* 图片上传
* 多语言页面
* 数据库连接
* 询盘表单
* SEO 元信息
* Sitemap 和 Robots.txt

同时，需要使用与生产主机尽量一致的 PHP/MySQL 环境进行验证。

### 第三步：准备发布文件

从已经测试通过的版本制作网站发布包。

发布包至少需要包含：

* 网站 PHP 程序文件
* HTML/CSS/JavaScript 等前端资源
* 图片及必要的媒体文件
* 路由和安全配置
* 数据库 SQL 文件（单独保存，不放到公开网站目录）
* 部署说明和回滚文档

注意，发布包应该是可以直接运行的版本，而不是需要服务器安装依赖的开发源码。

### 第四步：通过 FTP 上传文件

使用 FileZilla 等 FTP 客户端连接虚拟主机。

找到管理面板指定的网站根目录，将需要公开部署的文件上传到正确位置。

不要把数据库备份、Git 仓库、开发日志或者账号密码文件上传到可以被浏览器直接访问的目录。

### 第五步：使用 phpMyAdmin 导入数据库

在虚拟主机面板创建 MySQL 数据库。

打开 phpMyAdmin，选择正确的数据库并导入本地准备好的 SQL 文件。

之后配置网站的数据库连接信息。

如果网站已经存在旧数据，则需要先备份，再执行经过验证的增量 SQL，不能直接覆盖或删除原有数据库。

### 第六步：配置 HTTPS 并完成测试

网站文件和数据库部署完成后，绑定域名并设置 SSL。

随后检查首页、产品详情、后台登录、图片加载、询盘提交、多语言切换以及 Google Ads 转化追踪是否正常。

**我希望最终实现的是：本地打包 → FTP 上传 → SQL 导入 → 配置连接 → 网站运行。**

不需要登录服务器安装 Node.js，也不需要通过 PM2 启动后台服务。

## 九、以后能否让 Codex 自动生成并发布文章？

这是我计划继续研究的一个方向。

因为网站是 PHP 架构，并且部署在虚拟主机上，所以不能简单理解为：上传几段 PHP 代码，就能让主机每天自动运行本地 Codex。

一种可以研究的方案是让自己的 Windows 电脑承担 AI 内容生成任务。

工作流程可以设计为：

1. Windows 任务计划程序定时启动本地任务。
2. Codex 根据产品资料和关键词生成文章草稿。
3. 对内容进行检查，避免虚构产品参数和工程案例。
4. 生成或准备文章配图。
5. 通过安全认证的 PHP 发布接口上传文章与图片。
6. 后台保存草稿，审核通过后发布。
7. 自动更新文章页面与 Sitemap。

这套方案不要求额外购买一台云服务器，但需要本地电脑和任务程序在计划执行时处于可运行状态。

我更倾向于在初期保留人工审核，等生成质量和发布流程稳定后，再考虑更高程度的自动化。

## 十、使用 Codex 开发网站的一些经验

经过不断调整开发方案，我总结了几个比较重要的原则。

### 1. 先写文档，再让 AI 写代码

把网站结构、数据库字段、页面功能和部署要求写清楚，能明显减少后期返工。

### 2. 不要一次让 AI 重写整个网站

每次只完成一个明确的模块，例如产品管理、图片管理或文章发布。

### 3. 每个阶段都要进行测试

不要把“代码已经生成”当作“功能已经完成”。

尤其是后台权限、数据库写入、文件上传以及询盘提交，需要通过实际操作验证。

### 4. 使用 Git 保存稳定版本

每完成一个阶段，就保存对应版本和测试记录。

如果后续修改出现问题，可以定位具体差异并进行回滚。

### 5. 始终考虑真实部署环境

适合 VPS 或云服务器的技术方案，并不一定适合共享虚拟主机。

选型应该以项目需求、管理能力和服务器条件为基础。

### 6. 网站最终要为业务服务

对于 B2B 外贸网站来说，界面美观固然重要，但更重要的是产品信息完整、网站访问稳定、询盘入口清晰以及广告转化可以被正确统计。

## 十一、总结

使用 Codex 开发多语言外贸网站，最大的价值并不是让 AI 一次性生成一个看起来完整的网站，而是借助 AI 完成架构设计、模块开发、测试修复和持续优化。

对我的项目来说，从 Next.js + Node.js 调整为 PHP + MySQL，并不意味着放弃网站功能或可扩展性，而是选择了更适合当前虚拟主机条件的技术方案。

最终希望实现的是一个具备以下能力的 B2B 外贸独立网站：

* 管理员可以独立维护产品和网站内容
* 海外客户可以使用不同语言访问产品页面
* 网站具备规范的 SEO/GEO 基础
* 产品资料、技术参数和案例能够持续更新
* Google Ads 广告转化可以准确追踪
* 网站可以通过 FTP 和 phpMyAdmin 方便部署、维护和备份

目前我的项目仍在按照既定阶段继续开发和验收，后续也会继续记录 Admin 后台、多语言页面、SEO/GEO 以及自动化内容发布的具体实现过程。
